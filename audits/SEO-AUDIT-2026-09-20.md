# SEO-audit aimi-development.nl — 20 september 2026

**Methode.** Volledige code-read van de TanStack Start-codebase (`src/`, `scripts/`,
`supabase/migrations/`, `public/`), plus analyse van de gearchiveerde live-crawl in
`aimi-development.nl-audit/tmp/` (raw HTML van de productieserver, zonder JS-executie).

**Wat NIET geverifieerd kon worden — lees dit eerst.**
De live site was vanuit deze sessie niet bereikbaar: de egress-proxy weigert elke
CONNECT naar `aimi-development.nl:443` met HTTP 403 (`curl: (56) CONNECT tunnel failed`,
bevestigd via `__agentproxy/status`: `connect_rejected ×4`). Er is dus **geen verse
live-crawl, geen verse statuscode-check, geen verse CWV-meting** in dit rapport.

Daardoor is het volgende **niet** vastgesteld en staat het expliciet als open punt:

| Niet verifieerbaar | Nodig om te bevestigen |
|---|---|
| Actuele statuscodes, redirect-ketens, www/https-varianten | `curl -I` vanaf een machine met toegang |
| Of blogpagina's daadwerkelijk SSR-HTML leveren in productie | `curl -A Googlebot https://aimi-development.nl/blog/<slug>` |
| Impressie-/positiedata, welke URL's zijn gedegradeerd | Search Console-export "Prestaties" + "Pagina's" (laatste 90 dagen) |
| Downtime rond deploys | `pm2 logs aimi-digital-craft --lines 2000`, `/var/log/nginx/error.log` |
| Core Web Vitals velddata | CrUX / PageSpeed Insights per URL |
| Nginx-config (staat niet in de repo) | `nginx -T` op de VPS |
| Backlinkprofiel, Google Bedrijfsprofiel | Ahrefs/Search Console-links, GBP-dashboard |

Alles hieronder dat **wél** een bestand + regelnummer of een HTML-snippet heeft, is hard bewijs.

## 1. Executive summary — de 5 belangrijkste bevindingen

1. **De site is géén CSR-app. De aanname in de opdracht klopt niet.**
   Dit is TanStack Start met `node-server` SSR (`vite.config.ts:6-9`). De gearchiveerde
   productie-HTML bevat vóór JS-executie al de `<h1>`, de canonical, 68 interne
   `<a href>`-links en de JSON-LD. Een "CSR-only blog" is daarmee als oorzaak van de dip
   uitgesloten — tenzij een verse fetch iets anders laat zien (zie open punten).

2. **Het deploy-script legt de site plat voor de duur van elke build.**
   `scripts/deploy.sh:23-26` doet `pm2 stop` vóór `npm ci` en `vite build`. Tussen die
   momenten draait er niets op de PM2-poort en geeft Nginx 502. Bij 4 deploys in 2 dagen
   rond de bloguitrol (16-17 sept) zijn dat 4 vensters van elk minuten waarin Googlebot
   502's kan hebben opgehaald. Dit is het enige mechanisme in de codebase dat een
   *plotselinge, site-brede* impressiedaling kan verklaren.

3. **De sitemap publiceert 10 blog-URL's dubbel, met tegenstrijdige `lastmod`.**
   `src/routes/sitemap[.]xml.tsx:19-42` emit eerst álle `PAGE_DATES`-paden — inclusief 10
   `/blog/<slug>`-entries (`src/lib/seo.ts:137-147`) — en daarná dezelfde posts nogmaals
   uit de database. Beide keren met een andere datum. Dit is ontstaan bij de bloguitrol.

4. **47 elementen worden server-side gerenderd met `opacity:0`**, inclusief de `<h1>` van
   de homepage. De LCP-kandidaat is dus letterlijk onzichtbaar tot `motion` gehydrateerd is.
   Dit raakt élke pagina en staat los van de blog.

5. **De snippets zijn niet klikbaar gemaakt.** 33 van de 51 titles beginnen met exact
   dezelfde woorden ("Website laten maken …") en de homepage-`<h1>` is
   "Websites die écht werken." — zonder enig zoekwoord. Bij positie 63 is CTR 0,1%
   primair een *positie*probleem, maar de snippet maakt het niet beter.

**Toegevoegd/gewijzigd dat SEO raakt:**

- Nieuwe routes: `src/routes/blog.tsx`, `src/routes/blog_.$slug.tsx`
- `src/routes/sitemap[.]xml.tsx` — blogposts uit de DB toegevoegd (`1727351`, +3 regels)

- `src/server.ts` — nieuwe redirect-middleware uit een DB-tabel (`+40` regels)

- `src/lib/markdown.tsx` — eigen markdown-renderer (géén externe library)
- Migraties: 57 blogposts in totaal

**Wat NIET is gewijzigd:** geen aanpassing aan `public/robots.txt`, geen wijziging in
`__root.tsx`-canonical-logica (die bestaat daar niet — canonicals staan per route),
geen noindex-wijziging. De 51 publieke routes hebben allemaal precies één canonical
(geverifieerd per bestand); `__root.tsx` zet er géén, dus er is geen kans op een dubbele
of conflicterende canonical via een gedeeld layout-component.

**Bevinding A1-1 — HOOG — Downtime ingebakken in elke deploy**

- **Probleem:** de app staat gestopt tijdens `npm ci` + `vite build`.
- **Bewijs:** `scripts/deploy.sh:23-26`
  ```bash
  echo "==> app stoppen (voorkomt crash-loop tijdens build)"
  pm2 stop aimi-digital-craft || true
  echo "==> build (node-server preset geforceerd)"
  NITRO_PRESET=node_server npm run build
  ```
- **Oorzaak:** de stop is bewust toegevoegd om een crash-loop te voorkomen (zie comment
  regel 14-16), maar lost dat op ten koste van volledige onbereikbaarheid.
- **Fix:** bouw naar een tijdelijke map en swap pas ná een geslaagde build:
  ```bash
  NITRO_PRESET=node_server npm run build            # app blijft draaien op oude .output
  [ -f .output/server/index.mjs ] || exit 1
  pm2 reload aimi-digital-craft --update-env        # reload i.p.v. stop+start
  ```
  Vereist dat de build niet in de live `.output` schrijft; bouw naar `.output-new` en
  `mv` die erover vlak vóór de reload. Downtime gaat dan van minuten naar <1 seconde.
- **Te bevestigen:** `pm2 logs aimi-digital-craft --lines 2000` en de Nginx `error.log`
  rond 2026-09-16 08:41, 22:31 en 2026-09-17 10:43/16:41. Zoek naar `connect() failed`
  / `502`. Vergelijk met de crawl-statistieken in Search Console
  (Instellingen → Crawlstatistieken → "Hostreacties").

**Bevinding A1-2 — De blogpagina's zijn niet CSR-only (aanname weerlegd)**

- **Bewijs:** `aimi-development.nl-audit/tmp/home.html` is de raw productie-HTML en bevat
  zonder JS al:
  ```html
  <title>AIMI — Webdesignbureau uit Veendam | Websites &amp; webshops</title>
  <link rel="canonical" href="https://aimi-development.nl/"/>
  <h1 class="text-white max-w-3xl" style="...">Websites die écht<br/>werken.</h1>
  ```
  plus 68 `<a href="/...">`-links en JSON-LD (`FAQPage`, `WebSite`, `Organization`).
- De blogroutes gebruiken hetzelfde mechanisme: `loader` draait server-side, `head()`
  leest `loaderData` (`src/routes/blog_.$slug.tsx:36-100`). Content, title, canonical en
  JSON-LD zitten dus in de initiële HTML.
- **Kanttekening:** dit bestand dateert van vóór de bloguitrol (de bijbehorende
  `tmp/sitemap.xml` bevat 48 URL's en géén blog-URL's). **Verifieer alsnog** met
  `curl -A "Googlebot" https://aimi-development.nl/blog/checklist-nieuwe-website | grep -c "<h1"`.

**Bevinding A1-3 — MIDDEL — De blog-loader haalt de volledige tekst van álle posts op**

- **Probleem:** `/blog` selecteert `content` van elke gepubliceerde post, alleen om
  leestijd te berekenen. Die volledige tekst wordt in de SSR-payload geserialiseerd.
- **Bewijs:** `src/routes/blog.tsx:19-27`
  ```ts
  .select("slug, title, excerpt, content, published_at")
  ```
  en `blog.tsx:206` gebruikt hem alleen voor `estimateReadTime(post.content)`.
- **Impact:** 10 live posts × ~500 woorden ≈ 30 KB extra. Bij 57 posts (maart 2027)
  wordt dat ~170 KB extra op één pagina, dubbel: één keer in de HTML, één keer in de
  hydration-JSON.
- **Fix:** bereken de leestijd bij het opslaan en sla hem op als kolom
  (`read_minutes int`), of gebruik `word_count`. Haal `content` uit de list-query.

### A2 — Kannibalisatie door de nieuwe blogs

**Bevinding A2-1 — HOOG (maar nog niet live) — Directe slug-collisie**

- **Probleem:** er bestaat zowel een statische pagina `/wordpress-of-maatwerk` als een
  blogpost met slug `wordpress-of-maatwerk`. Twee URL's, één zoekwoord, één intentie.
- **Bewijs:**
  - Route: `src/routes/wordpress-of-maatwerk.tsx`, title *"WordPress vs maatwerk website:
    eerlijke vergelijking | AIMI"*, opgenomen in `PAGE_DATES` (`seo.ts:110`), in de footer
    (`Footer.tsx:38`) en in `llms.txt:18`.
  - Blogpost: `supabase/migrations/20260917120000_blog_batch2_new_posts_scheduled.sql:1557`
    → `'wordpress-of-maatwerk',`

- **Status:** deze post staat op `scheduled` met een datum in batch 2 (nov 2026+), dus
  **hij is nu nog niet live**. Dit is dus een te voorkomen probleem, geen huidige oorzaak.
- **Fix nu:** hernoem de slug vóór publicatie (bv. `wordpress-of-maatwerk-verschil`) of
  schrap de post en link vanuit de blog naar de bestaande pagina. Voeg daarna een

### A3 — Indexatie-impact

**Bevinding A3-1 — HOOG — Dubbele URL's in `sitemap.xml` met tegenstrijdige `lastmod`**

- **Probleem:** elke van de 10 initiële blogposts staat twee keer in de sitemap, met
  twee verschillende `lastmod`-waarden.
- **Bewijs:** `src/routes/sitemap[.]xml.tsx:19-25` bouwt `staticUrls` uit **álle**
  `PAGE_DATES`-entries:
  ```ts
  const staticUrls = Object.entries(PAGE_DATES).map(([path, lastmod]) => ...)
  ```
  `PAGE_DATES` bevat sinds de uitrol ook blogposts (`src/lib/seo.ts:136-147`):
  ```ts
  // Blog
  "/blog": "2026-09-16",
  "/blog/wordpress-site-gehackt": "2026-09-16",
  ...
  "/blog/checklist-nieuwe-website": "2026-09-16",
  ```
  Regel 33-42 voegt daarna dezelfde posts nogmaals toe uit de database:
  ```ts
  const blogUrls = (posts ?? []).map((p) => `<loc>${BASE_URL}/blog/${p.slug}</loc>
      <lastmod>${p.updated_at.slice(0, 10)}</lastmod>`)
  const urls = [...staticUrls, ...blogUrls];
  ```
  Dat die 10 slugs daadwerkelijk `published` in de DB staan, blijkt uit
  `20260916120000_blog_cms_module.sql:162` → `'published', '2026-09-16T09:00:00Z', ...`.
  Migratie `20260917110000_blog_batch2_seo_update_existing.sql` doet `UPDATE` op deze
  posts, waardoor de trigger `blog_posts_touch_updated_at` (`cms_module.sql:33-35`)
  `updated_at` op 17 sept zette — de twee `lastmod`-waarden lopen dus aantoonbaar uiteen.
- **Oorzaak:** de blog-URL's zijn aan `PAGE_DATES` toegevoegd voor de zichtbare
  "Bijgewerkt op"-regel, zonder te zien dat de sitemap over dezelfde map itereert.
- **Impact:** een sitemap met dubbele `<loc>` en tegenstrijdige `lastmod` is een direct
  kwaliteitssignaal richting Google; de `lastmod`-waarden worden onbetrouwbaar geacht en
  genegeerd. Bovendien meldt `scripts/indexnow-submit.mjs:18` deze dubbele lijst aan
  Bing/Yandex.
- **Fix:** filter blogpaden uit de statische lijst.
  ```ts
  const staticUrls = Object.entries(PAGE_DATES)
    .filter(([path]) => !path.startsWith("/blog/"))
    .map(([path, lastmod]) => ...)
  ```
  Laat `/blog` (de indexpagina) er wél in staan. De `PAGE_DATES`-entries blijven nodig
  voor `webPageJsonLd()`, dus verwijder ze niet — filter alleen in de sitemap.

**Bevinding A3-2 — Soft 404's: mechanisme is correct opgezet, live-check nodig**

- Een onbekende slug gooit `notFound()` (`blog_.$slug.tsx:47`), waarna TanStack Router
  `notFoundComponent` rendert. `src/server.ts:296-303` zet daarop `X-Robots-Tag: noindex`
  bij status 404, en `server.ts:245-270` corrigeert de dubbele `<title>`.
- Dit is goed doordacht. **Maar niet live geverifieerd.**
  Check: `curl -sI https://aimi-development.nl/blog/bestaat-niet` → verwacht
  `HTTP/2 404` + `x-robots-tag: noindex`. Geeft dit 200, dan is er wél een soft 404.

**Bevinding A3-3 — Geplande posts lekken niet (correct)**

- Zowel de RLS-policy (`cms_module.sql:49`) als beide loaders filteren op
  `status = 'published' AND published_at <= now()`. Een geplande post is dus niet
  opvraagbaar en staat niet in de sitemap.
- Geen publieke staging-omgeving aangetroffen in de repo. `wrangler.jsonc` bestaat nog uit
  de Lovable/Cloudflare-tijd — **controleer of er geen oude Cloudflare Pages-deploy
  (`*.pages.dev`) nog publiek en crawlbaar is.** Dat zou een volledig duplicaat van de
  site zijn. Dit is een reëel risico en niet vanuit de repo vast te stellen.

### A4 — Performance-regressie door de blogs

- **Bundle:** de markdown-renderer is eigen code zonder dependencies
  (`src/lib/markdown.tsx`, 160 regels, geen imports buiten React/Router). Er is **geen**
  syntax-highlighter of markdown-library toegevoegd. `package.json` kreeg bij de
  bloguitrol geen nieuwe runtime-dependency. De JS-bundle van niet-blogpagina's is dus
  **niet** opgeblazen door de blog. Hypothese weerlegd.
- `vite.config.ts:13-30` splitst recharts/motion/dnd/radix in aparte chunks, met een
  doordachte `utils`-chunk om te voorkomen dat `cn()` de recharts-chunk meetrekt. Goed.
- **Wél toegevoegd:** `public/videos/werkwijze.mp4` (2,0 MB) in commit `f80d1a3`.
  Die laadt lazy (`werkwijze.tsx:104` — `{inView && <video preload="none">}`), dus alleen
  op `/werkwijze` en pas bij scroll. Acceptabel, maar 2 MB in git is veel; overweeg
  een kleinere encode of WebM.
- **CWV-meting:** niet uitgevoerd — live site onbereikbaar. Zie B8 voor wat de code
  aantoonbaar fout doet.

### A5 — Conclusie Deel A

**Meest waarschijnlijke scenario (gerangschikt op bewijskracht):**

1. **Crawlfouten door deploy-downtime.** Vier deploys in 32 uur, elk met een venster
   waarin de site 502 geeft (`deploy.sh:23-26`). Googlebot die in zo'n venster crawlt,
   registreert hostfouten; Google verlaagt dan tijdelijk de crawlfrequentie voor de hele
   host, wat zich uit als een site-brede impressiedaling — precies het patroon dat
   beschreven wordt. **Dit is het enige mechanisme in de codebase dat site-breed werkt.**
   *Bevestigen met:* Search Console → Instellingen → Crawlstatistieken → Hostreacties.
2. **Sitemap-integriteit.** De dubbele `<loc>` met tegenstrijdige `lastmod` (A3-1) is
   exact gelijktijdig ontstaan en ondermijnt het versheidssignaal van de hele sitemap.
3. **Normale volatiliteit bij een jonge site.** 190 → 80 impressies is in absolute zin
   klein. Bij gemiddelde positie 63 zitten vrijwel alle impressies op pagina 6+, waar
   minimale ranking-schommelingen al zichtbaar zijn in de impressiecijfers. Zonder
   Search Console-export is **niet vast te stellen** of dit een oorzaak-gevolgrelatie is
   of samenvallende ruis. Dat is een eerlijke uitkomst, geen ontwijking.

**Uitgesloten op basis van bewijs:** CSR-only blog (A1-2), bundle-opblazing (A4),
link dilution door de blog (A2-3), massale contentdump (A2-4), noindex/canonical-regressie
via een gedeeld component (A1).

## 3. DEEL B — Site-brede audit

### B1 — URL-inventaris (baseline)

51 publieke routes + 1 dynamische blogroute. Volledige tabel in §6.

**Niet-publieke routes** (correct afgeschermd): `/login` (noindex, wel crawlbaar zodat de
noindex gelezen kan worden), `/admin*`, `/portal*`, `/account`, `/server`, `/api/*`,
`/track.js` — allemaal in `robots.txt` geblokkeerd.

**Weespagina's (geen interne link ernaartoe):**
- `/blog/<slug>` — alleen bereikbaar via `/blog`. Niet in de footer, niet in `llms.txt`,
  geen gerelateerde-artikelen-blok onderaan een post. Blogposts linken *naar* elkaar via
  markdown (`post_links`), maar er is geen zichtbaar "lees ook"-blok gerenderd:
  `BlogPostLinksPanel.tsx` is een **admin**-component, geen publieke render.
- `/meer-diensten` — alleen via nav-dropdown en footer, niet contextueel gelinkt.

**Doodlopende pagina's:** geen. Elke publieke pagina rendert de `Footer` met 52 links.

### B2 — Crawlability & indexatie

**robots.txt** (`public/robots.txt`) — regel voor regel:

| Regel | Beoordeling |
|---|---|
| `User-agent: * / Allow: /` | Correct |
| `Disallow: /portal /admin /account /server /api/ /track.js` | Correct, geen SEO-waarde |
| Comment: `/login blijft crawlbaar` | Correct doordacht |
| AI-crawlers expliciet `Allow` (GPTBot, OAI-SearchBot, PerplexityBot, ClaudeBot, Google-Extended, CCBot, …) | Bewuste keuze, gedocumenteerd |
| `Disallow` voor Bytespider, PetalBot, MJ12bot | Correct |
| `Sitemap: https://aimi-development.nl/sitemap.xml` | Aanwezig |

**Bevinding B3-1 — HOOG — 47 elementen worden SSR'd met `opacity:0`**

- **Probleem:** de volledige zichtbare content wordt server-side gerenderd met
  `opacity:0` en een `translateY`, en pas zichtbaar gemaakt zodra `motion` is
  gehydrateerd. De LCP-kandidaat (de `<h1>`) is dus onzichtbaar tot de JS-bundle is

- **Bewijs:** in `aimi-development.nl-audit/tmp/home.html` komt `opacity:0` **47 keer**
  voor. De `<h1>` zelf:
  ```html
  <h1 class="text-white max-w-3xl" style="...;opacity:0;transform:translateY(20px)">
    Websites die écht<br/>werken.</h1>
  ```
  Bron: `src/components/Hero.tsx:52` e.v. en de `motion.*`-componenten met

  2. Gebruik `<MotionConfig>` met een `isHydrated`-flag: render `initial={false}` tijdens
     SSR en de eerste client-render.

### B8 — Core Web Vitals & performance

**Niet gemeten** (live site onbereikbaar). Wat de code aantoonbaar doet:

**Problemen:**
1. **`opacity:0` op de LCP-elementen** — zie B3-1. Grootste hefboom.
2. **Blogafbeeldingen zonder dimensies** — zie B4-6. CLS op elke post met een afbeelding.
3. **`/blog` laadt de volledige tekst van alle posts** — zie A1-3. Groeit naar ~170 KB.
4. **`motion` zit in de kritieke bundel.** De raw HTML toont
   `<link rel="modulepreload" href="/assets/motion-Bp-EBsJ0.js"/>` op de homepage.
   Omdat de zichtbaarheid van alle content ervan afhangt (B3-1), is dit render-blocking
   in de praktijk. **Fix:** los B3-1 op; dan wordt `motion` een progressieve verbetering
   i.p.v. een voorwaarde.
5. **`public/videos/werkwijze.mp4` = 2,0 MB.** Lazy geladen (`werkwijze.tsx:104`,
   `preload="none"`, alleen `{inView &&}`), dus alleen op `/werkwijze` bij scroll.
   Acceptabel, maar overweeg WebM + een lagere bitrate.

**Wat goed is:**
- **Compressie:** Brotli (quality 11) en gzip (level 9) worden op applicatieniveau
  toegepast met een in-memory cache per pad+encoding, async zodat de event loop niet
  blokkeert, en met een `Vary: Accept-Encoding` (`server.ts:169-228`). Zeer degelijk
  opgelost, juist omdat Nginx het niet deed.
- **Caching:** content-gehashte assets krijgen `max-age=31536000, immutable`; statische
  publieke bestanden 1 uur (`server.ts:132-156`). Correct onderscheid.
- **Fonts:** self-hosted WebP-… pardon, self-hosted woff2 (`public/fonts/`, 56 KB totaal),
  met `<link rel="preload" as="font" crossOrigin>` op de primaire latin-subset
  (`__root.tsx:139-145`). Geen externe font-request. Voorbeeldig.
  **Wel controleren:** staat er `font-display: swap` in de `@font-face` in `styles.css`?
- **Code splitting:** doordachte `manualChunks` met een expliciete `utils`-chunk om te
  voorkomen dat `cn()` de 383 KB recharts-chunk meetrekt (`vite.config.ts:13-30`).
- **Hero-image:** srcset, sizes, dimensies, fetchPriority, auto-preload. Zie B4.
- **Speculation Rules:** prefetch op `/contact`, `/tarieven`, `/website-laten-maken`
  met `eagerness: "moderate"` (`__root.tsx:246-258`). Goede keuze.

**TTFB:** niet gemeten. Let op: `server.ts:358-372` doet vóór élke request een
`checkRedirect()` die bij een koude cache een Supabase-roundtrip vereist
(`server.ts:324-338`, TTL 60s). Op een lege cache kost dat tientallen ms op de eerste
request na elke minuut. **Fix:** verleng de TTL naar 5 minuten en ververs de cache
achtergrondmatig i.p.v. op de hot path, of laad de redirects bij het opstarten.

**Third-party scripts:** exact één — `/track.js` (eigen, first-party), en die laadt
**alleen na cookie-consent** (`AnalyticsLoader.tsx:29-40`). Calendly staat in de CSP
toegestaan maar wordt niet in de gelezen componenten geladen. Geen Google Analytics,
geen Tag Manager, geen Facebook Pixel. Voor performance is dat ideaal.

### B10 — Server, security & infrastructuur

**Nginx:** de config zit **niet in de repo**. `aimi-development.nl-audit/NGINX-FIXES.md`
bevat een eerder opgestelde stappenlijst (versienummer verbergen, etc.), wat suggereert
dat er nog openstaande serverpunten zijn. **Nodig:** `sudo nginx -T > nginx-dump.txt`.

**Security headers** (`server.ts:117-145`) — allemaal aanwezig:
`X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`,
`Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`,
`Strict-Transport-Security: max-age=31536000; includeSubDomains` (alleen over https,
`server.ts:297-299`).

**Bevinding B10-1 — De CSP blokkeert de structured data niet (geverifieerd)**
De CSP bevat `script-src 'self' 'unsafe-inline' https://assets.calendly.com`
(`server.ts:130-138`). JSON-LD staat in `<script type="application/ld+json">`, en
CSP `script-src` geldt niet voor niet-uitvoerbare scripttypes. Bovendien is
`'unsafe-inline'` toegestaan (nodig voor de TanStack-hydration-bootstrap, met een
eerlijke risico-afweging in de comment). **Geen probleem.**

**Bevinding B10-2 — LAAG — `default-src 'self'` zonder `form-action`**
De CSP mist `form-action 'self'`. Het contactformulier post naar een server function op
dezelfde origin, dus functioneel geen probleem, maar het is een gratis hardening-regel.

**Bevinding B10-3 — HSTS zonder `preload`**
`max-age=31536000; includeSubDomains` staat er; `preload` niet. Dat is een bewuste,
verdedigbare keuze (preload is moeilijk terug te draaien). Laat zoals het is, tenzij
alle subdomeinen — inclusief `portal.aimi-development.nl` (`email.server.ts:27`) —
gegarandeerd https zijn.

**PM2:** `ecosystem.config.cjs` met `min_uptime: "10s"`, `max_restarts: 10`,
`restart_delay: 2000` — expliciet toegevoegd na een crash-loop die de site platlegde
(zie comment regel 25-27). Dat er ooit zo'n crash-loop is geweest, is relevant voor Deel A.
**Check:** `pm2 describe aimi-digital-craft` → kolom `restarts`. Een hoog getal wijst op
terugkerende crashes.

**Monitoring:** er is een eigen foutregistratie — `server.ts:19-35` logt SSR-crashes naar
de `site_errors`-tabel, `__root.tsx:70-85` logt client-side errorboundary-crashes, en er
is een Alerts-scherm in de admin. Dat is meer dan de meeste sites van deze omvang hebben.
**Maar:** er is geen uptime-monitoring van buitenaf en geen alert op statuscode-afwijkingen.
Zie §7.

### B14 — Analytics & meetbaarheid

**Bevinding B14-1 — HOOG — Analytics meet alleen bezoekers die cookies accepteren**
- **Bewijs:** `AnalyticsLoader.tsx:29-40` laadt `/track.js` uitsluitend als
  `prefs?.analytics === true` in localStorage staat.
- **Oorzaak:** bewust, om te doen wat het privacybeleid belooft. Juridisch de juiste keuze.
- **Impact:** typisch 40-70% van het verkeer wordt niet gemeten. Elke conversieratio en
  elk bezoekersaantal is dus structureel een onderschatting — en de cijfers zijn niet
  vergelijkbaar met Search Console, dat álle klikken telt.
- **Fix:** voeg een cookieloze basistelling toe (server-side pageview-logging op de
  SSR-request, zonder identifier) náást de cookie-gebaseerde tracking. Dat vereist geen
  toestemming en geeft een betrouwbaar totaal. Het datamodel bestaat al: `site_ping`
  en `site_errors` (`src/routes/api/public/site-ping.ts`).

**Bevinding B14-2 — MIDDEL — Conversies worden niet aantoonbaar gemeten**
Er is geen event-registratie gevonden voor formulierinzending, telefoonklik (`tel:`) of
mailklik (`mailto:`). De contactinzending gaat naar Supabase (`leads`) en per mail, maar
wordt niet als conversie-event vastgelegd naast de pageviews.
**Fix:** log een `conversion`-event bij een geslaagde `submitContactForm`, en voeg
click-handlers toe op de `tel:`/`mailto:`-links in de footer.

**Bevinding B14-3 — Search Console-koppeling niet verifieerbaar.**
**Nodig:** controleer dat er een **Domain property** (`aimi-development.nl`) bestaat, niet
alleen een URL-prefix-property. Een domain property vangt alle varianten (http/https,
www/non-www, subdomeinen) in één rapport — met een URL-prefix-property mis je data en zie
je een dip die deels een meetartefact is.

**Bevinding B14-4 — Geen alert op indexatie- of statuscode-afwijkingen.**
Er is eigen foutlogging (`site_errors`) maar geen externe uptime-monitor en geen
sitemap-/statuscode-bewaking. Zie §7.

## 7. Preventie — hoe je een herhaling voorkomt

### 7.1 Zero-downtime deploys (lost de meest waarschijnlijke dip-oorzaak op)

Vervang in `scripts/deploy.sh` de stop-build-start-volgorde:

```bash
echo "==> build (app blijft draaien)"
NITRO_PRESET=node_server npm run build
[ -f .output/server/index.mjs ] || { echo "FOUT: build mislukt" >&2; exit 1; }

echo "==> zero-downtime reload"
pm2 reload aimi-digital-craft --update-env
```

Schrijft de build in de live `.output`, dan eerst naar `.output-new` bouwen en pas ná de
sanity-check `mv`-en. Downtime gaat van minuten naar minder dan een seconde.

### 7.2 Pre-deploy checks in de pipeline

Voeg vóór de reload toe:

```bash
npm run lint
npx tsc --noEmit
node scripts/check-seo-invariants.mjs   # nieuw, zie 7.3
```

### 7.3 Nieuw script: `scripts/check-seo-invariants.mjs`

Laat de deploy falen bij elk van deze condities — allemaal fouten die dit rapport heeft
aangetroffen en die stil hadden kunnen blijven:

1. Een pad komt meer dan één keer voor in de gegenereerde sitemap.
2. Een publieke route uit `routeTree.gen.ts` ontbreekt in `PAGE_DATES`.
3. Een `PAGE_DATES`-pad begint met `/blog/` (die horen alleen uit de DB te komen).
4. Een blog-slug botst met een statische route of met een `CORE_PAGES`-pad.
5. Een publieke route heeft geen canonical, of meer dan één.
6. Een title is leeg of langer dan 60 tekens; een description korter dan 120 of langer
   dan 165.
7. `robots.txt` bevat `Disallow: /` op `User-agent: *`.

### 7.4 Post-deploy smoke test

Direct na de reload, vóór `indexnow-submit`:

```bash
for p in / /blog /website-laten-maken /contact /sitemap.xml /robots.txt; do
  code=$(curl -s -o /dev/null -w "%{http_code}" "https://aimi-development.nl$p")
  [ "$code" = "200" ] || { echo "FOUT: $p gaf $code"; exit 1; }
done
# een niet-bestaande URL moet 404 geven, geen 200 (soft 404)
[ "$(curl -s -o /dev/null -w "%{http_code}" https://aimi-development.nl/bestaat-niet-xyz)" = "404" ] \
  || { echo "FOUT: soft 404"; exit 1; }
```

### 7.5 Monitoring en alerts

- **Externe uptime-monitor** (UptimeRobot/BetterStack, gratis tier) op `/` en `/sitemap.xml`,
  interval 1 minuut, alert per e-mail én Telegram (de Telegram-webhook bestaat al:
  `src/routes/api/telegram/webhook.ts`).
- **Search Console**: zet e-mailmeldingen aan voor indexeringsproblemen.
- **Wekelijkse cron** die de sitemap ophaalt, elke `<loc>` een `HEAD`-request geeft en
  alarmeert bij een niet-200, een duplicaat, of een aantal-URL's-afwijking >10% t.o.v.
  vorige week.
- **Maandelijks handmatig**: Search Console → Crawlstatistieken → Hostreacties. Elke piek
  in "Serverfout (5xx)" correleert met een deploy en is direct terug te voeren op §7.1.

### 7.6 Checklist bij elke contentuitrol

Vóór publicatie van een blogpost of nieuwe pagina:

- [ ] Slug botst niet met een bestaande route (`src/routes/*.tsx`) of met `CORE_PAGES`.
- [ ] Zoekintentie verschilt aantoonbaar van bestaande pagina's op hetzelfde thema.
- [ ] Minstens één contextuele link naar de bijbehorende dienstpagina.
- [ ] De eerste alinea beantwoordt de titelvraag letterlijk (AI-citeerbaarheid).
- [ ] `seo_title` ≤ 60 tekens, `seo_description` 140-160 tekens met CTA.
- [ ] Featured image heeft een beschrijvende `alt`, plus `width`/`height`.
- [ ] Na publicatie: URL staat precies één keer in `/sitemap.xml`.
- [ ] Na publicatie: `curl -A Googlebot <url> | grep "<h1"` levert de titel op.

## 8. Wat dit rapport bewust níét beweert

  autoriteit (B13), niet techniek.
- Enige uitspraak over backlinks, concurrentie-actualiteit, CWV-velddata, Nginx-config of

  genoemd.
